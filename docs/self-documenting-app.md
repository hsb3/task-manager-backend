# Convention — Self-Documenting App (`app_docs`)

We keep a collection, **`app_docs`**, that documents the rest of the app. The
documentation lives *inside* PocketBase as data, so it travels with the app,
is queryable at runtime, and shows up in backups.

## Why

- PocketBase has **no native collection description** (a collection only stores
  name/type/fields/rules/indexes). This fills that gap.
- **Docs travel with the app.** Seeded via a migration, they rebuild on any
  fresh DB — no separate wiki to keep in sync or forget to deploy.
- **Self-describing API.** A client can `GET /api/collections/app_docs/records`
  and render help/onboarding straight from the backend.

## Shape

One record per documented thing. Fields:

| Field | Purpose |
|-------|---------|
| `slug` | stable unique key, `namespace:name` (e.g. `collection:tasks`) — and the record's classification, since the namespace IS the category. The namespace is optional (a bare `name` is legal) but when present must be one of `collection` \| `concept` \| `decision` \| `hook` \| `route`; PocketBase refuses anything else with a 400. Unique index. |
| `title` | short human title |
| `refName` | the collection it documents; blank for concepts and most routes |
| `body` | markdown text (portable — any client renders it) |

**Access:** public read (`listRule`/`viewRule` = `""`), superuser write.
Schema in [`../schema/app_docs.json`](../schema/app_docs.json).

## Field help

Every non-system collection field carries its own help text in its migration;
`scripts/check_field_help.ts` refuses a field without one. A view rebuilds its fields from its
query on every boot, so a view column's help lives in `scripts/view_field_help.ts`.
`scripts/gen_openapi.ts` publishes both in `openapi.json`.

## How it travels (the important part)

- **Schema** → the collection's auto-generated migration (like every collection).
- **Content** → an **idempotent data-seed migration** generated by
  `scripts/gen_app_docs_seed.ts` (the newest seed is its `DEFAULT_OUTPUT`). Each seed upserts
  the WHOLE collection by `id`, so the highest-numbered seed wins at boot. Making a new seed, and the
  digest that pins its prose (`scripts/app_docs_seed.sha256`): `.agents/rules/pocketbase.md`.

`down()` is a deliberate no-op (any fresh boot re-establishes the seed), so a revert leaves
the prose in place and a re-apply re-upserts it by id; `scripts/check_app_docs_down_up.ts`
gates that round trip against span loss. Note the boundary: **schema + docs travel via
migrations; user/sample data does not** (that's `scripts/seed.ts`).

## The rule (the convention)

**A collection, route, hook, or notable decision added or changed carries its
`app_docs` record in the same change**: regenerate the seed (`.agents/rules/pocketbase.md`),
never hand-edit it. Keep the `slug` stable so it upserts, not duplicates.

Docs-as-data can drift from the real schema, so the convention is **enforced
automatically** (below), not left to discipline.

## Enforcement (CI + pre-commit)

[`../scripts/check_app_docs.ts`](../scripts/check_app_docs.ts) fails if any
non-system collection lacks a `collection:<name>` doc. It replays `pb_migrations/`
into a throwaway DB (no server/port/auth) and compares `_collections` against
`app_docs`, so it checks exactly what ships.

- **Pre-commit:** [`../lefthook.yml`](../lefthook.yml) runs it on every commit, inside
  `make check-static`. `make setup` installs Lefthook and activates the hook.
- **CI:** [`../.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs `make check-static`,
  which includes it.

```bash
bun scripts/check_app_docs.ts   # ✅ all N collections documented  /  ❌ lists the gaps
```

(A commit-time gate catches drift before it ships, rather than a runtime hook blocking
server startup in prod.)

## Read it

```bash
# public, no auth needed; dev server (`make dev`)
curl -s "http://127.0.0.1:8090/api/collections/app_docs/records?sort=slug"
curl -s "http://127.0.0.1:8090/api/collections/app_docs/records?filter=slug~'collection:'"
```
